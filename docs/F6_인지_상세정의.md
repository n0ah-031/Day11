## 1. 처리 흐름 전체 개요

```
[첨부 업로드]                     [문답 (recognize 모드)]                [등록]
xlsx 첨부 ──▶ 사전 검증(§2.1) ──▶ 구조 추출(§3) ──▶ 필드 추론(§4)      ──▶ register(§6)
              ├ 확장자·매직바이트      ├ 헤더 탐지        ├ 규칙 기반 선추론        ├ 원본 무변형 이동
              ├ xlsm 거부             ├ 헤더 결합        ├ LLM 의미 보완          ├ field_rules upsert
              └ 크기·구조 상한        ├ 데이터 영역      ├ confidence 판정         └ 세션 close
                                     ├ 서식·유효성      └ 확인 질문(low만, §5)
                                     └ 샘플 행(마스킹)
```

- 구조 추출(§3)은 **결정적(deterministic) 알고리즘**이다 — 동일 파일이면 동일 `structural_json`이 나온다. LLM은 §4의 의미 추론(타입·필수 여부의 업무적 판단)과 확인 질문 생성에만 관여한다.
- 기술명세 v0.1 §4의 상태 머신, §5의 API 골격은 그대로 유지한다. 본 문서는 각 단계의 내부 규칙과 오류 처리를 채운다.

## 2. 첨부 사전 검증 (업로드 시점)

### 2.1 recognize 후보 첨부의 검증 순서

`POST /projects/{id}/form-intake/attachments` 처리 중, 세션 모드와 무관하게(모드 판정 전일 수 있음) 아래를 적용한다.

| 순서 | 검사 | 실패 시 응답 |
|---|---|---|
| 1 | 확장자 허용 목록: `xlsx` `hwpx` `png`(F1 공용). 단 **recognize 모드 확정 후에는 png 첨부를 거부** | `415 UNSUPPORTED_FORMAT` — "인지·등록에는 png를 사용할 수 없습니다" |
| 2 | **매크로 포함 확장자 조기 거부**: `xlsm` `xlsb` `xltm`은 첨부 시점에 즉시 거부(기술명세 v0.1은 register 시점 검증만 규정 — 본 문서에서 첨부 시점으로 앞당김, §13 C10) | `400 MACRO_NOT_ALLOWED` — "매크로 포함 파일(xlsm 등)은 보안 정책상 등록할 수 없습니다" |
| 3 | 매직바이트: xlsx는 zip 시그니처 `PK\x03\x04` + `[Content_Types].xml` 존재 확인(확장자 위변조 방지) | `400 REGISTER_VALIDATION_FAILED` (detail: `magic_byte`) |
| 4 | 크기: 파일당 50MB(PRD §6.1 준용, J6) | `400 FILE_TOO_LARGE` |
| 5 | 구조 상한: 시트 ≤ 10, 셀 합계 ≤ 10,000 (F1 §6.3 재사용). openpyxl `read_only` 모드로 로드하여 검사 | `422 STRUCTURE_LIMIT_EXCEEDED` — 초과 항목·수치를 메시지에 포함 |
| 6 | 손상 검사: openpyxl 로드 실패(zip 손상, OOXML 파싱 실패) | `400 REGISTER_VALIDATION_FAILED` (detail: `corrupt`) |

- 통과한 xlsx는 즉시 §3 구조 추출을 수행하고, 결과 요약(시트 수·헤더 후보·샘플 행 유무)을 업로드 응답의 `extracted_summary`에 담는다. 성명 계열 열이 감지되면(§9.2) `has_name_column: true`를 함께 반환한다.
- xlsx 첨부가 1개면 자동으로 `primary_attachment_id` 후보 지정, 2개 이상이면 라디오 UI로 명시 선택(기술명세 v0.1 §5.2·§8 그대로).

### 2.2 hwpx 참고 첨부

- 등록 대상 불가(F6-2). F1 §6.5 `extractor.py` 텍스트 추출을 그대로 사용해 참고 컨텍스트로만 어댑터에 전달. 업로드 응답에 `registrable: false`를 포함해 프론트가 "참고 자료로만 활용됩니다" 인라인 안내를 렌더한다.

## 3. 구조 추출 엔진 (`services/form_structure.py`)

xlsx 전용. openpyxl(값 모드 + 서식 접근)로 시트를 순회하며 `structural_json`(§3.6)을 생성한다.

### 3.1 시트 선별

- 숨김 시트(`sheet_state != 'visible'`)와 차트 시트는 추출 대상에서 제외하되, `skipped_sheets`로 기록해 확인 질문/검수 표에 노출한다(사용자가 몰랐던 시트 누락 방지).
- 사용 영역이 완전히 빈 시트도 `skipped_sheets`(사유: `empty`)로 기록.

### 3.2 헤더 행 탐지 (휴리스틱, K3)

각 시트에서 상단 `min(20, 사용 행 수)`행을 스캔하고, 행별 점수를 계산해 최고점 행을 기본 헤더 행으로 선정한다.

| 신호 | 조건 | 점수 |
|---|---|---|
| S1 채움 밀도 | 사용 열 범위 내 비어있지 않은 셀 비율 ≥ 0.6 | +2 |
| S2 텍스트 비율 | 값이 있는 셀 중 문자열 타입 비율 ≥ 0.8 | +2 |
| S3 하부 타입 대비 | 아래 1~3행의 동일 열 값들이 숫자·날짜·빈칸 등 이질 타입이거나, 아래가 전부 빈 행(빈 양식 패턴) | +2 |
| S4 서식 신호 | bold 또는 배경색 채움 셀 비율 ≥ 0.5 | +1 |
| S5 값 유일성 | 행 내 문자열 값에 중복 없음 | +1 |
| S6 전폭 병합 감점 | 행 전체가 하나의 병합 셀(제목 행 패턴) | −3 |

- 동점이면 **아래쪽(데이터에 가까운) 행**을 선택.
- `header_confidence` 판정: 최고점 ≥ 6 → `high`, 그 외 → `low`. `low`면 §7.2의 헤더 범위 확인 질문이 **반드시** 발생한다.
- 최고점 < 3이면 해당 시트는 "구조 인지 실패"로 표시하고, 모든 시트가 실패하면 첨부를 등록 불가 처리한다(`422 NO_RECOGNIZABLE_STRUCTURE`, 안내: "표 형태의 헤더를 찾지 못했습니다").

### 3.3 다중 행 헤더 블록 결합 (K3)

기본 헤더 행 `r`을 기준으로 위쪽으로 확장을 시도한다.

1. **확장 조건**: 행 `r-1`이 (a) 텍스트 값 존재, (b) 전폭 병합(제목 패턴) 아님, (c) 헤더 열 범위 일부에 걸치는 **가로 병합 셀이 존재하거나** S1~S5 점수 ≥ 4 — 를 모두 만족하면 헤더 블록에 편입. 같은 방식으로 최대 3행까지 반복.
2. **결합 규칙**: 블록 내 각 행에서 가로 병합 셀은 병합 범위의 모든 열에 값을 전개(forward-fill)하고, 병합이 아니어도 빈 셀은 좌측 값으로 forward-fill한다. 열별로 상위 행 → 하위 행 순으로 `"-"`로 조인해 필드명을 만든다(예: 1행 `예산` + 2행 `편성액` → `예산-편성액`). 상·하위 값이 동일하면 1회만 사용.
3. **필드명 정규화·유일화**: 앞뒤 공백 제거, 개행은 공백 치환, 연속 공백 축약. 시트 내 중복 필드명은 `필드명(2)`, `필드명(3)` 접미사로 유일화하고 `structural_json`에 `dedup: true`를 표시(검수 표에서 배지 노출).
4. 다중 행 블록이 만들어진 경우 `header_confidence`는 **무조건 `low`로 강등**한다 — 결합 결과의 타당성을 사용자 확인 질문으로 검증하기 위함(§7.2).

### 3.4 데이터 영역·샘플 행

- **시작**: 헤더 블록 마지막 행 + 1.
- **끝**: 시작 행부터 아래로 스캔하며 **연속 빈 행 3개**를 만나면 그 직전을 `data_end_row`로 확정. 데이터가 전혀 없으면 `data_end_row: null`(빈 양식, E5).
- 데이터 영역 하단에 다시 텍스트 밀집 행이 나타나면(합계 행·주석 등) 데이터로 취급하지 않고 `footer_rows`로 기록만 한다(집계행이 샘플로 오염되는 것 방지 — 판정: 해당 행에 `합계`/`총계`/`계` 문자열 또는 수식 존재).
- **샘플 행**: 데이터 영역 상위 최대 **5행**(K6)을 열별 dict로 추출. LLM 전달본은 §9.2 마스킹 파이프라인을 거친 후 사용하고, DB 저장본(`structural_json`)은 마스킹 이전 원문을 보존한다(기술명세 v0.1 §6.2 정책 유지).

### 3.5 열 메타데이터 추출

열 범위는 헤더 블록에서 필드명이 만들어진 열로 한정한다(헤더 없는 잉여 열은 무시하되 `extra_columns`로 기록).

| 항목 | 추출 규칙 |
|---|---|
| `existing_number_format` | 데이터 영역 셀들의 number_format **최빈값**(General 제외 우선). 데이터가 없으면(빈 양식) 헤더 바로 아래 행 셀의 서식 사용. 그래도 General이면 `"General"` |
| `existing_validation` | `worksheet.data_validations`에서 해당 열의 데이터 영역과 교차하는 규칙. `list` 타입은 source 해석 — 인라인(`"기획팀,인사팀"`)은 분할, 범위 참조(`=Sheet2!$A$1:$A$5`)는 대상 범위 값을 읽어 최대 50개까지 해석(초과·해석 불가 시 raw 문자열을 `source_raw`로 보존) |
| `filled_ratio` | 데이터 영역 내 해당 열 채움 비율(0~1). 빈 양식이면 null. §4.2 required 추론 근거 |
| `sample_values` | 해당 열 샘플 최대 5개(마스킹 후, LLM 전달용) |

### 3.6 structural_json 스키마 (v2 — 기술명세 v0.1 §6.2 스키마를 대체, §13 C7)

```jsonc
{
  "schema_version": 2,
  "sheets": [
    {
      "name": "예산집행현황",
      "title_rows": [1],                    // 전폭 병합 등 제목으로 판정된 행
      "header_rows": [3, 4],                // 다중 행 헤더 블록 (단일이면 원소 1개)
      "header_confidence": "high",          // high | low (§3.2, §3.3)
      "data_start_row": 5,
      "data_end_row": 42,                   // 빈 양식이면 null
      "footer_rows": [43],                  // 합계 행 등 (§3.4)
      "merged_regions": ["A1:F1", "C3:D3"],
      "columns": [
        {
          "letter": "C",
          "header": "예산-편성액",
          "header_parts": ["예산", "편성액"],  // 다중 행 결합 시 근거 보존
          "dedup": false,
          "existing_number_format": "#,##0",
          "existing_validation": { "type": "list", "source": ["기획팀","인사팀"], "source_raw": null },
          "filled_ratio": 1.0,
          "sample_values": ["1200000", "800000"]   // LLM 전달본에서만 존재(마스킹 후)
        }
      ],
      "sample_rows": [ { "부서명": "기획팀", "집행일자": "2026-03-02", "예산-편성액": 1200000 } ]
    }
  ],
  "skipped_sheets": [ { "name": "참고", "reason": "hidden" } ],
  "extra_columns": []
}
```

- **LLM 전달 시 절단 규칙(K12)**: 시트당 열 최대 60개, `sample_rows` 최대 5행, 전체 직렬화 길이 첨부당 최대 12,000자 — 초과 시 열 우선순위(왼쪽부터)로 절단하고 `truncated: true` 표기. DB 저장본은 절단하지 않는다(상한 §2.1-5가 이미 총량을 제한).

## 4. 필드 추론 — 규칙 선추론 + LLM 의미 보완

추론은 2층이다: **①규칙 기반 선추론**(백엔드, 결정적)이 `structural_json`에서 타입·형식·필수 후보와 confidence를 만들고, **②LLM(`recognize_turn`)**이 헤더의 업무적 의미로 보완·교정한다. LLM은 규칙 선추론이 `high`로 확정한 값을 **뒤집을 수 없다**(프롬프트 계약 + 백엔드 가드 §4.4).

### 4.1 타입·형식 추론 우선순위 (규칙 선추론)

근거 우선순위: **기존 유효성 검사 > number_format > 샘플 값 패턴 > 헤더명 의미(LLM 몫)**.

| 근거 | 추론 결과 | confidence |
|---|---|---|
| validation `type=list` | 헤더가 부서 계열(부서·팀·과·소속 포함)이면 `dept_code`, 아니면 `text` + `rule_config_json.allowed_values`에 목록 저장 | high |
| validation `type=date` | `date` | high |
| number_format이 날짜 계열: `yyyy-mm-dd`, `yyyy/m/d`, `yyyy"년" m"월" d"일"`, `mm/dd` 등 | `date` + format 매핑(아래 표) | high |
| number_format이 통화·천단위: `#,##0`, `#,##0.00`, `₩#,##0`, `"₩"...` | 헤더에 금액 의미어(금액·비용·예산·단가·액)가 있으면 `amount`, 없으면 `number` | 금액 의미어 있으면 high, 없으면 low |
| number_format `0`, `0.00`, 백분율 `0%` | `number` | high |
| number_format `@`(텍스트 서식) | `text` | high |
| General + 샘플 값 존재 | 샘플 5개 전부 날짜 파싱 가능 → `date`(low) / 전부 숫자 → `number`(low) / 그 외 → `text`(low) | low |
| General + 샘플 없음(빈 양식) | LLM 의미 추론에 위임 | low |
| 헤더가 성명 계열(§9.2 목록) | `name` | high |

**number_format → field format 문자열 매핑표** (field_rules `rule_config_json.format`에 저장되는 표준 표기):

| number_format | format |
|---|---|
| `yyyy-mm-dd` | `YYYY-MM-DD` |
| `yyyy/m/d`, `yyyy/mm/dd` | `YYYY/MM/DD` |
| `yyyy"년" m"월" d"일"` | `YYYY년 M월 D일` |
| `mm/dd`, `m/d` | `MM/DD` (연도 없음 — 확인 질문 유발, low) |
| `#,##0` | `숫자, 천 단위 구분` |
| `0` | `숫자만, 구분기호 없음` |
| `0.00` | `숫자, 소수 2자리` |
| `0%` | `백분율` |
| (매핑 불가 커스텀 서식) | raw 서식 문자열 보존 + low → 확인 질문 |

### 4.2 필수 여부(required) 추론

| 근거 | 판정 | confidence |
|---|---|---|
| 헤더 텍스트에 `*`, `(필수)`, `[필수]` | `required: true` (표식은 필드명에서 제거하고 `notes`에 기록) | high |
| 헤더 텍스트에 `(선택)`, `(해당 시)` | `required: false` | high |
| 샘플 ≥ 3행이고 `filled_ratio = 1.0` | `required: true` 후보 | low |
| 샘플 ≥ 3행이고 `filled_ratio < 0.5` | `required: false` 후보 | low |
| 빈 양식 또는 샘플 < 3행 | LLM 의미 추론(예: 키 성격 필드는 필수 추정) | low |

- 기술명세 v0.1 §6.3의 원칙 유지: **구조로 명확해도 업무적 의미가 모호하면 low** — required는 셀만으로 확정할 수 없는 대표 항목이므로 high 조건(헤더 표식)이 없는 한 low가 기본이다.

### 4.3 spec_json 확장 스키마 (recognize 모드)

F1 §6.2 스키마에 시트 귀속(K2)과 추론 메타를 추가한다.

```jsonc
{
  "form_title": "예산 집행 현황(외부 확정 양식)",   // 파일명·제목 행에서 LLM이 제안, 사용자 수정 가능
  "fields": [
    {
      "sheet": "예산집행현황",          // K2: 시트 귀속 (recognize 모드 필수)
      "source_column": "C",            // structural_json.columns.letter와 1:1
      "name": "예산-편성액",
      "type": "amount",                // F1과 동일 enum: text|number|amount|date|name|dept_code
      "required": true,
      "format": "숫자, 천 단위 구분",
      "allowed_values": null,          // list validation에서 파생 시 배열
      "notes": null,
      "confidence": "high",            // high | low (이진, K5)
      "evidence": "number_format #,##0 + 헤더 '편성액'"   // 검수 표 근거 툴팁용
    }
  ],
  "source_attachment_ids": ["uuid"],
  "locale": "ko"
}
```

### 4.4 백엔드 가드 (LLM 응답 후처리)

`recognize_turn` 응답의 spec_json에 대해 매 턴 검증한다. 위반 시 해당 필드를 규칙 선추론 값으로 되돌리고 어댑터에 위반 사실을 피드백(최대 2회 재요청, F1 §6.1 정책 준용).

1. `structural_json`의 (sheet, column) 조합과 `fields[].{sheet, source_column}`이 1:1 — 필드 임의 추가·삭제 금지
2. 규칙 선추론 confidence `high` 필드의 `type`·`format`·`allowed_values` 변경 금지 (`required`는 사용자 답변으로만 변경 가능)
3. `confidence`는 상향만 가능하되, **사용자 답변이 근거일 때만** low → high 승격(LLM 자의 승격 금지 — 직전 턴에 해당 필드 확인 질문이 있었는지 백엔드가 대조)
4. enum·필수 속성 검증(F1 §6.1 structured output 스키마 강제와 동일)

## 5. AI 어댑터 프롬프트 계약

### 5.1 `classify_intent` (첫 턴 전용)

- **입력**: 첫 사용자 메시지(마스킹 후), `has_xlsx_attachment: bool`, 첨부 파일명 목록.
- **출력(structured)**: `{ "intent": "generate" | "recognize" | "ambiguous", "reason": string }`
- **백엔드 선행 가드**: xlsx 첨부가 없으면 LLM이 `recognize`를 반환해도 `ambiguous`로 강등하고 reply에 "기존 양식을 등록하려면 xlsx 파일을 첨부해 주세요"를 포함시킨다(등록 대상 없는 recognize 모드 진입 방지).
- **판정 기준(시스템 프롬프트 계약)** — 기술명세 v0.1 §4.2를 few-shot으로 구체화:

| 발화 예 | 첨부 | intent |
|---|---|---|
| "이 양식 그대로 써야 해요" / "외부에서 받은 확정 양식입니다" | xlsx | recognize |
| "이 파일 참고해서 비슷하게 새로 만들어줘" | xlsx | generate |
| "부서별 예산 집행 현황 양식 만들어줘" | 없음 | generate |
| "이거요" / "이 파일이요" (의도 표현 없음) | xlsx | ambiguous |
| "이 양식 그대로 쓸 건데 항목 두 개만 추가해줘" | xlsx | **generate** (원본 변형 요구 = 재저작 필요 → F1. reply에 "기존 양식을 수정하려면 새 양식 생성으로 진행됩니다" 안내) |

- `ambiguous` 처리: 기술명세 v0.1 §4.2 그대로 — mode null 유지, 인라인 버튼 2개("새 양식 만들기" / "첨부한 파일 그대로 등록")로 사용자가 확정. 버튼 선택은 `POST .../messages`에 `forced_mode: "generate"|"recognize"` 필드로 전달한다(§6.1 API 확장).

### 5.2 `recognize_turn`

- **입력**: 대화 이력(마스킹 후) + 현재 spec_json + structural_json(LLM 전달본, §3.6 절단 규칙 적용) + hwpx 참고 텍스트(있으면).
- **출력(structured)**: `{ "reply": string, "spec_json": {...전체 갱신본}, "recognize_complete": bool }`
- **시스템 프롬프트 계약(요지)**:
  1. 너의 역할은 양식을 새로 만드는 것이 아니라, 주어진 구조 추출 결과의 각 필드에 대해 **업무적 의미를 보완**하는 것이다. 필드를 추가·삭제하거나 confidence high 필드의 타입·형식을 바꾸지 마라.
  2. `confidence: "low"` 필드만 확인 질문 대상이다. **한 턴에 최대 3개 필드**를 묶어 질문하라(K7). 각 질문은 선택지형으로(예: "'비고'는 필수 입력인가요? — 필수 / 선택").
  3. 사용자 답변으로 확인된 필드는 값을 갱신하고 confidence를 high로 올려라. 사용자가 "모르겠다"고 하면 합리적 기본값을 채우되 confidence는 low로 유지하라.
  4. low 필드가 없거나 전부 1회 이상 질문을 거쳤으면 `recognize_complete: true`를 반환하라.
  5. 헤더 범위 확인 질문(§7.2)이 필요한 시트가 있으면 **다른 필드 질문보다 먼저** 처리하라(헤더가 바뀌면 필드 목록 전체가 재추출되므로).

### 5.3 확인 질문 정책 (E7 구체화)

- 질문 발생 조건(우선순위 순): ① `header_confidence: low` 시트의 헤더 범위 확인 → ② §4.3 루브릭 위반 항목(date/amount인데 format 없음 등) → ③ confidence low 필드의 required/type 확인.
- **턴 상한 10**(기술명세 v0.1 §4.3-4 유지). 초과 시 남은 low 항목을 목록으로 직접 제시하고 검수 표에서 일괄 수정하도록 안내.
- 완결성 루브릭(기술명세 v0.1 §4.3)을 K2에 맞춰 개정(§13 C8):
  1. `structural_json` **모든 시트의** 모든 헤더가 `spec_json.fields`에 (sheet, source_column) 기준 1:1 매핑
  2. 모든 field에 `type`·`required`·`confidence` 존재
  3. `date`/`amount` 타입 field는 `format` 존재
  4. `header_confidence: low` 시트가 남아 있으면 미완(헤더 확인 질문 미소화 상태)
  5. **confidence low 잔존은 완료를 차단하지 않는다** — 단 1회 이상 질문을 거쳤어야 하며(`asked_fields` 세션 추적), 잔존 시 등록 확인 단계에서 "확인 필요 n건" 경고를 노출(§7.3). 사용자가 답을 모르는 경우의 교착 방지

## 6. API 상세 (기술명세 v0.1 §5의 보완)

### 6.1 재사용·확장 엔드포인트 추가 사항

- `POST /projects/{id}/form-intake/messages` 요청에 `forced_mode?: "generate" | "recognize"` 추가 — ambiguous 인라인 버튼 선택 전달용(§5.1). `forced_mode`가 오면 intent 판정을 생략하고 해당 모드로 확정.
- 헤더 범위 확인 질문에 대한 답변은 일반 메시지가 아니라 구조화 필드로 전달: `header_override?: { "sheet": "예산집행현황", "header_rows": [2, 3] }` — 수신 시 백엔드가 해당 시트를 **§3 알고리즘으로 재추출**(지정 헤더 행 고정)하고 spec_json 필드를 재생성한다. 이때 이미 사용자 답변으로 확정된 다른 시트 필드는 보존.

### 6.2 register 처리 시퀀스 (`POST /projects/{id}/form-templates/register`)

동기 처리, 타임아웃 15초(J1). 단계와 보상(compensation) 처리:

| 단계 | 동작 | 실패 시 |
|---|---|---|
| 1 | 세션 검증: `mode='recognize'` ∧ `spec_complete=true` ∧ `primary_attachment_id` 존재 | `409 SPEC_NOT_COMPLETE` / `409 SESSION_MODE_MISMATCH` / `400 NO_PRIMARY_ATTACHMENT` |
| 2 | 첨부 재검증: tmp 파일 존재, 매직바이트·확장자·크기 재확인(§2.1 3~6과 동일 — 첨부 후 세션이 길어진 사이의 변조·TTL 삭제 대비) | `400 REGISTER_VALIDATION_FAILED` (detail 포함) |
| 3 | `template_id` 채번, Storage **복사**: `tmp/{session_id}/{attachment}` → `forms/{project_id}/{template_id}_v{version}.xlsx`. 복사 후 원본·사본 바이트 해시 대조(무변형 보증, E1) | 사본 삭제 후 `500 REGISTER_FAILED` |
| 4 | DB 트랜잭션: `form_templates` insert(status='done', source='recognized_external', structural_json 스냅샷, workbook_json=NULL) + `field_rules` upsert(§6.3) + `intake_sessions.status='closed'` | 트랜잭션 롤백 + **3단계 사본 삭제(보상)** 후 `500 REGISTER_FAILED` |
| 5 | tmp 첨부 삭제(비 primary 포함) | 실패해도 응답은 성공 유지, 경고 로그만(TTL 7일 정리로 수습, F1 J4 준용) |
| 6 | `audit_logs`에 `form_register` 기록, 응답 반환 | — |

- Storage를 "이동"이 아니라 **복사 후 삭제**로 구현하는 이유(K9): Supabase Storage move가 중간 실패하면 원본 유실 가능 — 복사·검증·트랜잭션 완료 후 원본을 지우는 순서가 무변형 보증(E1)과 정합.
- 15초 타임아웃 초과 시 `500 REGISTER_TIMEOUT` + 보상 처리. 프론트는 재시도 버튼 노출(멱등성: 동일 세션 재요청 시 이전 실패의 잔여 사본이 있으면 정리 후 재실행).

### 6.3 field_rules upsert 규칙 (K2 반영)

- `spec_json.fields[]` → 필드당 1행: `(form_template_id, sheet_name, field_name)` 조합을 유일 키로 upsert.
- `rule_type` = `fields[].type` 그대로(enum 정렬 완료). `rule_config_json`에 저장: `format`, `required`, `allowed_values`(있으면), `source_column`, `confidence`(등록 시점 스냅샷 — 검수 이력용).
- F1 §3.4와 동일하게 **백엔드가 기계적으로 파생**하며 LLM 재호출 없음.

### 6.4 오류 코드 총괄표 (F6 관련 신규)

| HTTP | code | 발생 지점 |
|---|---|---|
| 415 | `UNSUPPORTED_FORMAT` | recognize 모드에서 png 첨부(§2.1-1) |
| 400 | `MACRO_NOT_ALLOWED` | xlsm 등 첨부(§2.1-2) |
| 400 | `FILE_TOO_LARGE` | 50MB 초과(§2.1-4) |
| 422 | `STRUCTURE_LIMIT_EXCEEDED` | 시트 >10 또는 셀 >10,000(§2.1-5) |
| 422 | `NO_RECOGNIZABLE_STRUCTURE` | 전 시트 헤더 탐지 실패(§3.2) |
| 400 | `REGISTER_VALIDATION_FAILED` | 매직바이트·손상·재검증 실패(detail: `magic_byte`/`corrupt`/`missing`) |
| 400 | `NO_PRIMARY_ATTACHMENT` | 등록 대상 미지정(§6.2-1) |

## 7. 프론트엔드 상세 (화면 3 인지 모드)

기술명세 v0.1 §8의 표를 전제로, 본 문서에서 확정한 인터랙션만 추가한다.

### 7.1 검수 표 (field_rules 검수·수정)

| 컬럼 | 내용 |
|---|---|
| 시트 | K2 — 시트 탭 또는 그룹 헤더로 구분 표시 |
| 필드명 | `dedup: true`면 "중복명 자동 구분" 배지 |
| 타입 / 형식 / 필수 | 인라인 편집 가능(드롭다운·토글). 편집 시 §5.4 PATCH 페이로드에 반영 |
| 허용값 | `allowed_values` 칩 목록, 편집 가능 |
| 신뢰도 | "확인됨"(high) / "확인 필요"(low) 배지 — 기술명세 v0.1 §8 유지 |
| 근거 | `evidence` 툴팁(예: "기존 서식 #,##0에서 추론") |

### 7.2 헤더 범위 확인 질문 UI

- `header_confidence: low` 시트 발생 시, 챗 버블에 해당 시트 상단 `min(10, data_start_row+2)`행의 **read-only 미니 그리드**를 렌더하고 탐지된 헤더 블록 행을 하이라이트.
- 퀵리플라이 2개: "헤더가 맞아요"(→ 일반 메시지로 확정 전달) / "직접 지정"(→ 미니 그리드에서 행 클릭·드래그로 범위 선택 → `header_override`로 전송, §6.1).
- 원본 구조 미리보기(우측 결과 영역)도 `structural_json`의 `title_rows`/`header_rows`/`data_start_row`를 색 구분으로 표시해 사용자가 인지 결과를 시각적으로 검증할 수 있게 한다.

### 7.3 등록 확인 모달 (K4 고지 포함)

"이대로 등록하기" 클릭 시 모달로 최종 확인:
- 요약: 파일명, 시트 수, 필드 수, "확인 필요" 잔존 건수(있으면 경고 톤).
- **샘플 데이터 고지(K4)**: `data_end_row`가 null이 아닌 시트가 하나라도 있으면 — "이 파일에는 예시 데이터 n행이 포함되어 있으며, 원본 그대로(데이터 포함) 저장됩니다. 배포 전 데이터 정리가 필요하면 다운로드 후 직접 수행해 주세요."
- 확인 시 register 호출(동기) → 성공 시 결과 영역 전환(원본 구조 미리보기 + 검수 표 + 다운로드 버튼).

## 8. F2 취합 연동 계약 (F6-6, K2)

F2-5 전처리가 등록 양식을 참조할 때의 매칭 규칙. F2 측 구현은 `F2_취합_엑셀_상세정의.md` 범위이며, 여기서는 **접점 계약만** 정의한다.

1. **템플릿 선택**: 취합 프로젝트에 연결된 `form_templates` 최신 버전의 `field_rules`를 로드. `source`가 `ai_generated`든 `recognized_external`이든 동일 경로(F6-6).
2. **시트 매칭**: 회신 파일 시트명 ↔ `field_rules.sheet_name` — ① 정확 일치 → ② 정규화 일치(K10: 앞뒤·연속 공백 제거, 전각→반각, casefold. **괄호 주석 제거는 적용하지 않음** — `현황(상반기)`/`현황(하반기)` 오매칭 방지) → ③ 실패 시 해당 시트는 "작성 기준 없음"으로 처리하고 F2-5의 기존 흐름(사용자가 기준 지정)으로 위임. `예산집행현황(3월)`처럼 괄호 변형이 붙은 시트도 ③으로 위임된다.
3. **하위 호환**: `sheet_name`이 NULL인 field_rules(기존 F1 생성분)는 **모든 시트에 공통 적용**(현행 동작 유지). F1 생성 양식도 이후 시트명을 채우도록 개정 제안(§13 C6).
4. **필드 매칭**: 시트 매칭 후 헤더명 기준 — 정규화 규칙은 ②와 동일. `필드명(2)` 접미사(§3.3-3)는 매칭 전 원문 그대로 비교(회신 파일도 같은 양식이므로 동일 중복이 존재하는 것이 정상).

## 9. 보안 상세

### 9.1 AI 전송 동의 — 기술명세 v0.1 §9.1 그대로. 추가로 §7.3의 샘플 데이터 고지(K4)는 동의와 별개로 등록 시점마다 노출한다.

### 9.2 마스킹·성명 열 감지

- 마스킹 적용 지점: `structural_json` **LLM 전달본**의 `sample_rows`·`sample_values`, 대화 이력, hwpx 참고 텍스트. 정규식은 F1 §9.2와 동일(주민번호·전화번호·이메일).
- **성명 열 감지 규칙**: 헤더 정규화 후 다음 목록과 부분 일치 — `성명, 이름, 성함, 담당자, 작성자, 신청자, 대표자, 책임자`. 감지 시 recognize 모드 기본값 **"마스킹함"**(J4)으로 해당 열 샘플 값을 `[성명]` 치환하고, 업로드 응답 `has_name_column: true` + 프론트 토글(사용자가 해제 가능).
- 마스킹은 LLM 전달본에만 적용 — 타입 추론(§4.1)은 마스킹 **이전** 원문 기준으로 백엔드가 수행하므로 추론 정확도에 영향 없음(마스킹 치환 문자열이 샘플 패턴 판정을 오염시키지 않도록 순서 보장).

### 9.3 감사 로그 — 기술명세 v0.1 §9.4에 추가: `form_register` 기록 시 `detail`에 원본 파일 SHA-256 해시를 남긴다(무변형 등록의 사후 검증 근거).

### 11.2 골든 테스트 (출시 전, PRD 잔여 리스크 "F6 구조 인지 정확도" 대응)

대표 양식 10종 × 기대 spec_json 스냅샷 비교(LLM 구간은 confidence·질문 발생 여부만 검증):

1. 단일 헤더 빈 양식 2. 단일 헤더 + 샘플 데이터 3. 제목행 + 2행 병합 헤더 4. 안내문 다행 + 헤더 5. 드롭다운(list validation) 포함 6. 다중 시트(3개) 7. 날짜 커스텀 서식(`yyyy"년"...`) 8. 필수 표식(`*`) 헤더 9. 합계 행 포함 샘플 10. 성명·전화번호 포함 샘플(마스킹 경로 검증)

거부 케이스: xlsm, 시트 11개, 셀 10,001개, 손상 zip, 헤더 전무.

### 11.3 통합 시나리오

PRD §5 시나리오 4를 E2E로: 첨부 → intent=recognize → 확인 질문 1건 응답 → 등록 → **F2에 동일 양식 회신 파일 업로드 시 field_rules 자동 준용 확인**(F6-6, §8 매칭 규칙 포함).

## 12. 본 문서에서 내린 세부 판단

K1~K4는 §0(사용자 확정). 이하 K5~K14는 본 문서 작성 중의 세부 판단으로, **2026-07-22 사용자 검토를 완료**했다 — K10만 조정(괄호 주석 제거 미적용)되었고 나머지는 원안 유지로 확정.

| # | 판단 | 근거 |
|---|---|---|
| K5 | confidence는 high/low **이진** | UI 배지가 "확인됨/확인 필요" 2종(기술명세 v0.1 §8)이고, 3단계는 확인 질문 트리거 기준만 복잡하게 만듦 |
